# BA End-to-End AI Workflow
## Master Implementation Specification for an AI Coding Agent

> Amended by [implementation-decisions.md](implementation-decisions.md). Where the two disagree, the addendum wins.

## 1. Objective

Build an AI-driven Business Analyst workflow that supports the software development lifecycle from initial analysis through implementation, testing, documentation, and subsequent change requests.

The workflow must not behave as a collection of isolated prompts.

It must operate as a **stateful end-to-end workflow** where:

- every stage has clearly defined inputs;
- every stage produces standardized outputs;
- outputs from one stage become inputs for later stages;
- AI agents can access the relevant project context;
- specialized skills are used for repeatable BA activities;
- subagents may execute independent tasks in parallel;
- workflow progress is persisted;
- human approval is required at defined checkpoints;
- the workflow can stop and resume without losing its position;
- all generated artifacts remain traceable to requirements, use cases, system components, and implementation.

The target lifecycle is:

**Current-State Understanding → Requirement Elicitation → Overview Analysis → BA Planning → Detailed Specification → Technical Review → Coding → QA → User Guide → Change / Impact Analysis**

For an existing system, the workflow starts by reconstructing the current system from the source code. The workshop specifically treats source code as the primary representation of the current implementation and reconstructs architecture, APIs, screens, process relationships, and use cases before proceeding with new requirements.

# 2. Core Design Principles

## 2.1 AI must have project-wide visibility

The AI must be able to access all repositories that are relevant to the product.

Examples:

- frontend repositories;
- backend repositories;
- microservices;
- shared libraries;
- API definitions;
- database migration files;
- infrastructure/configuration files;
- existing BA artifacts generated by this workflow.

Do not merge repositories together.

Instead, expose them within the same AI-accessible workspace.

For VS Code, the recommended implementation is a **multi-root workspace** or a project root that references all required repositories.

Example:

```text
product-workspace/
│
├── frontend-app/
├── admin-portal/
├── backend-api/
├── payment-service/
├── notification-service/
├── shared-library/
│
└── ba-ai/
```

The AI must understand that these are separate repositories belonging to the same logical product.

---

## 2.2 Source code is the primary source for current-state reconstruction

For an existing product, do not assume that historical BA documentation accurately represents the implemented system.

Use the current codebase to reconstruct the current system.

Existing BA documents may be used as supplementary context or comparison material, but they must not override what is actually implemented.

The reconstructed current state should include:

- system architecture;
- applications;
- services;
- APIs;
- screens;
- entities;
- dependencies;
- use cases;
- business processes;
- validation logic where identifiable.

This follows the workshop's reverse-engineering approach before continuing into requirements and implementation.

---

## 2.3 Every workflow step must have an Input → Process → Output contract

Never create an undefined workflow stage.

For every step define:

```text
Input
↓
Processing Rules
↓
Output Artifact
↓
Validation
↓
Human Approval if required
↓
Next Step
```

Every output artifact must have an explicit downstream consumer.

Example:

```text
Elicitation Notes
↓
Overview Analysis
↓
Use Case List
↓
BA Planning
↓
Detailed Use Case Specification
↓
Coding
```

This standardization of each stage's input and output is one of the core principles described at the end of the workshop.

# 3. Workflow Operating Modes

The workflow must determine which route to execute.

There are three main operating modes.

## MODE A — Existing Product / Existing System

Use when the system already has source code.

Run:

```text
Reverse Engineering
        ↓
Current-State Approval
        ↓
Requirement Elicitation
        ↓
Overview Analysis
        ↓
BA Planning
        ↓
Detailed Specification
        ↓
Technical Review
        ↓
Coding
        ↓
QA
        ↓
User Guide
```

---

## MODE B — New Product / Major New Business Capability

Use when:

- a new product is being created;
- a major new business capability is introduced;
- the requested change significantly alters business processes;
- impact analysis determines that the change is too large for a normal CR.

Run:

```text
Requirement Elicitation
        ↓
Overview Analysis
        ↓
BA Planning
        ↓
Information Architecture
        ↓
Detailed Specification
        ↓
Technical Architecture
        ↓
Coding
        ↓
QA
        ↓
User Guide
```

---

## MODE C — Small Change Request

Use only for localized changes to an existing product.

Run:

```text
Change Request
       ↓
BA Knowledge Graph Query
       ↓
Impact Analysis
       ↓
Affected Use Cases
       ↓
Update Specifications
       ↓
Technical Review if required
       ↓
Coding
       ↓
QA
       ↓
Documentation Update
```

If impact analysis discovers a substantial new business flow or broad impact, stop the CR workflow and redirect the request to MODE B.

The workshop explicitly distinguishes small CRs from large changes and recommends routing major business changes back through the broader elicitation-to-analysis workflow.

# 6. Phase 0 — Workflow Bootstrap

## Purpose

Initialize or resume the BA workflow.

## Input

- user's request;
- existing workflow state if available;
- repository structure;
- existing BA artifacts.

## Process

1. Read `workflow/state.json`.
2. Identify project type:
   - new product;
   - existing product;
   - change request.
3. Identify all repositories.
4. Determine whether current-state documentation already exists.
5. Determine the active Epic / Use Case if one was provided.
6. Load only the context needed for the next phase.
7. Select the appropriate workflow route.

## Output

Updated:

```text
workflow/state.json
```

## Rule

The orchestrator must not perform detailed BA work itself when the work belongs to a specialized skill or subagent.

Its primary responsibility is:

**plan → delegate → validate → update state → control transition.**

# 7. Phase 1 — Current-State Reverse Engineering

## Execution condition

Run for existing systems.

Skip for a completely new product.

## Goal

Reconstruct the implemented system sufficiently for AI to understand how the product currently works.

## Inputs

- all relevant source repositories;
- API definitions;
- database schema/migrations;
- frontend routing;
- backend routing;
- service configuration;
- integration configuration.

Existing documentation may be used as a secondary reference.

## Required outputs

### 1. System Landscape

Identify:

- applications;
- users/actors;
- backend systems;
- services;
- external systems;
- third-party integrations.

Produce a C4-style representation where appropriate.

### 2. Application Inventory

For every application:

```yaml
application_id:
name:
type:
repository:
actors:
main_responsibilities:
dependencies:
```

### 3. Service Inventory

```yaml
service_id:
name:
repository:
responsibility:
upstream_dependencies:
downstream_dependencies:
data_entities:
apis:
```

### 4. API Catalog

Extract:

- endpoint;
- method;
- purpose;
- request;
- response;
- service owner;
- callers;
- downstream API calls.

### 5. Screen Catalog

Identify screens/pages/views.

For every screen record:

```yaml
screen_id:
application:
route:
purpose:
actors:
apis_called:
related_use_cases:
```

### 6. Dependency Chains

Reconstruct relationships such as:

```text
Screen
→ API
→ Service
→ Downstream API
→ Entity
```

### 7. Use Case Candidates

Infer system capabilities from screens, API behavior, data operations, and business logic.

### 8. Business Process Reconstruction

Group related use cases into business processes.

Do not assume inferred business processes are correct.

Mark them as:

```text
DRAFT_FROM_CODE
```

until reviewed by a BA.

### 9. Detailed Current-State Use Case Analysis

For each confirmed use case identify:

- trigger;
- actor;
- preconditions;
- main flow;
- alternate flows;
- validation;
- APIs;
- entities;
- screens.

This reconstruction approach—C4/system overview, APIs, screens, call hierarchy, business processes and detailed use-case behavior—is directly described in the workshop.

## Human Gate: CURRENT_STATE_REVIEW

Required reviewers:

- BA for business processes/use cases;
- SA/Developer for technical architecture where required.

Do not continue until the current-state baseline is sufficiently trustworthy.

# 8. Phase 2 — Requirement Elicitation Engine

## Goal

Transform stakeholder inputs into structured requirement knowledge.

## Inputs

Possible inputs include:

- stakeholder documents;
- meeting transcripts;
- emails;
- existing requirements;
- business requests;
- screenshots;
- user feedback;
- current-state analysis.

## Step 2.1 — Understand Current Need

Identify:

- current problem;
- affected users;
- business pain points;
- existing process;
- limitations;
- reason for change.

## Step 2.2 — Understand Future Need

Identify:

- desired outcome;
- future process;
- expected user behavior;
- expected system behavior;
- business goals.

## Step 2.3 — Gap Analysis

Compare:

```text
AS-IS
vs
TO-BE
```

Identify:

- process gaps;
- system gaps;
- data gaps;
- integration gaps;
- policy gaps;
- unresolved decisions.

## Step 2.4 — Generate Clarification Questions

Generate questions grouped by stakeholder.

Example categories:

- Business;
- Operations;
- Security;
- Data;
- Integration;
- Compliance;
- Technical;
- UX.

Each question must include:

```yaml
question:
reason:
impact_if_unanswered:
target_stakeholder:
priority:
status:
```

## Step 2.5 — Human Elicitation

AI must not simulate stakeholder decisions.

When stakeholder input is required:

```text
status = WAITING_FOR_HUMAN
```

The BA conducts the actual stakeholder discussion.

After the meeting, the BA provides meeting notes/transcript back into the workflow.

## Step 2.6 — Consolidate Elicitation

Merge:

- documents;
- previous findings;
- stakeholder answers;
- meeting notes;
- decisions.

Generate:

```text
requirements/elicitation/elicitation-summary.md
requirements/clarification-log/open-questions.md
requirements/assumptions/assumptions.md
```

# 10. Human Gate — OVERVIEW_APPROVAL

The workflow must stop for BA review.

At minimum the BA must confirm:

- business process;
- use case list;
- data model;
- critical business rules;
- state model where applicable.

If rejected:

```text

```

If approved:

```text

```

Proceed to BA Planning.

Possible status values:



# 13. Phase 5 — BA Specification Engine

This is one of the most important workflow engines.

Its job is to transform an approved overview/use case into a **code-ready functional specification**.

The workshop sequence is essentially:

**screen design → interactive HTML → sequence → activity/validation analysis → consolidated User Story/specification**, rather than writing the User Story first.

## Input

For each Use Case load only relevant context:

- product overview;
- related business process;
- use case;
- business rules;
- entities;
- current-state implementation if applicable;
- related APIs;
- affected application;
- design system;
- dependencies.

Do not load the whole project unnecessarily.

---

## Step 5.1 — Context Discovery

Build a context package containing:

```text
Use Case
Actor
Process Step
Business Rules
Entities
Existing Screens
Existing APIs
Related Use Cases
Design Constraints
```

Validate that required inputs exist.

If critical context is missing, stop and report the missing input.

---

## Step 5.2 — Functional Screen Design — Markdown

Generate the functional UI in a lightweight format first.

Output:

```text
ui/markdown/<UC-ID>.md
```

The artifact should define:

- screen purpose;
- sections;
- fields;
- buttons;
- actions;
- table columns;
- states;
- error states;
- validations;
- navigation;
- permissions.

---

# 14. Human Gate — UI_MARKDOWN_REVIEW

The workflow must stop.

BA reviews:

- screen flow;
- missing information;
- business behavior;
- usability;
- alignment with requirement.

Do not generate detailed prototype until approved.

# 15. Step 5.3 — Interactive HTML Prototype

After Markdown approval, generate an interactive prototype.

Output:

```text
ui/prototypes/<UC-ID>/
```

Prototype should support enough interaction to validate:

- navigation;
- states;
- controls;
- major user actions;
- validations;
- dialogs;
- success/error behavior.

The prototype is not production code.

Its purpose is requirement validation.

---

# 16. Human Gate — HTML_PROTOTYPE_REVIEW

BA or stakeholder reviews the interactive behavior.

If rejected:

```text
return → Step 5.2 / 5.3
```

If approved:

continue automatically.

The workshop explicitly places human review after the initial screen design and interactive HTML before allowing later technical analysis to proceed.

# 22. Phase 6 — Technical / SA Review

Because the BA specification contains API and technical-flow information, technical approval is required.

## Trigger

After BA approves the final specification.

The system may:

1. commit/push artifacts;
2. trigger a review hook;
3. create a review task/ticket;
4. notify the SA/Developer.

## SA review scope

Review:

- API design;
- service boundary;
- security;
- integration approach;
- architecture;
- database impact;
- performance concerns;
- technical feasibility.

The workshop describes an SA review checkpoint before coding when API specifications are produced, with the workflow waiting for technical confirmation or comments before continuing.

## Human Gate — TECHNICAL_APPROVAL

Possible results:

```text
APPROVED
CHANGES_REQUESTED
BLOCKED
```

When comments are received:

- ingest review comments;
- update affected artifacts;
- regenerate only impacted sections;
- preserve unaffected approved content;
- request re-review.

- technology stack;
- application architecture;
- database technology;
- repository structure;
- coding conventions;
- API conventions;
- security rules;
- logging standards;

- dependency rules;
- testing conventions.

Create:


# 24. Phase 7 — BA Coding Engine

## Precondition

All must be true:

```text
BA Specification = APPROVED
Technical Review = APPROVED
Technical Baseline = AVAILABLE
```

## Input

- approved specification;
- approved HTML prototype;
- API design;
- architecture rules;
- coding standards;
- existing source code;
- related entities;
- related tests.

## Process

1. Identify repositories affected.
2. Identify files/modules likely affected.
3. Generate an implementation plan.
4. Check whether implementation crosses service boundaries.
5. Modify the minimum necessary files.
6. Follow project conventions.
7. Add/update automated tests.
8. Validate compilation/linting.
9. Run relevant automated tests.
10. Record changed components.
11. Update BA Graph relationships if implementation introduces new components.

## Rule

Never rewrite unrelated modules.

Every major code change must trace to:

```text
Use Case
or
Acceptance Criterion
```

## Output

- code changes;
- implementation summary;
- changed-file list;
- automated test results.

Update:

```text
coding_status = WAITING_FOR_QA
```

The workshop workflow moves directly from approved specification into coding, with BA, SA, or Developer potentially triggering the coding agent depending on team structure.

Verify that implementation matches the approved requirements.

Generate tests from:

- Acceptance Criteria;
- main flows;
- alternate flows;
- error flows;
- business rules;
- validations;
- APIs;
- state transitions.

Test categories may include:

```text
Functional
Validation
API
Integration
Regression
Permission

```

---

## Step 8.2 — Execute Automated Tests

Where supported:

- run unit tests;
- run integration tests;
- run API tests;
- run UI automation;
- validate responses;
- validate business rules.

---

## Step 8.3 — Requirement Comparison

For every failed test:

```text
Expected behavior
vs
Actual behavior
```

Classify:

```text
CODE_DEFECT
SPECIFICATION_GAP
TEST_ISSUE
ENVIRONMENT_ISSUE
UNRESOLVED
```

---

## Step 8.4 — Automated Fix Loop

If classification is clearly:

```text
CODE_DEFECT
```

the coding agent may attempt a fix.

Then:

```text
Fix
→ Retest
→ Compare
```

Set a retry limit.

Do not create an infinite repair loop.

---

# 26. Human Gate — CRITICAL_FLOW_TEST

AI testing does not completely replace human testing.

Human testing is mandatory for:

- critical business journeys;
- high-risk processes;
- financial transactions;
- irreversible actions;
- security-sensitive operations;
- regulatory/compliance-sensitive behavior.

Lower-risk repetitive UI validation may rely more heavily on automated testing.

The workshop explicitly recommends AI testing first while keeping human validation for important flows and particularly high-risk or money-related scenarios.

## QA Outputs

```text
qa/test-cases/<UC-ID>.md
qa/test-results/<UC-ID>.md
qa/defects/<UC-ID>.md
```

Backlog:

```text
testing_status = DONE
```

only after required gates pass.

This workflow is for small changes to existing functionality.

## Input

```text

Business Rule
```

## Step 10.2 — Traverse BA Knowledge Graph

Example:

If an Entity changes:

```text
Entity
→ Use Cases using Entity
→ Screens
→ APIs
→ Business Rules
→ Test Cases
```

If an API changes:

```text
API
→ Calling Screens
→ Calling Services
→ Related Use Cases
→ Downstream APIs
```

If a Process Step changes:

```text
Process Step
→ Use Cases
→ Screens
→ Rules
→ APIs
→ Entities
```

The workshop proposes exactly this type of graph-based impact reasoning: identify affected use cases from changed entities, APIs, business rules, or process steps, then inspect them to determine whether the change causes real impact.

# 30. Step 10.4 — Change Size Classification

Classify the CR:

### SMALL

Localized modification with limited impact.

Continue:

```text
Impact Analysis
→ Spec Update
→ Coding
→ QA
```

### LARGE

Examples:

- new end-to-end process;
- major business capability;
- broad data-model redesign;
- many use cases affected;
- architecture change;
- major integration change.

Do not continue as a small CR.

Redirect:

```text
Requirement Elicitation
→ Overview Analysis
→ Planning
→ Detailed Specification
→ ...
```

# 32. Agent Architecture

Implement one primary orchestrator plus specialized subagents.

## Main Agent

### `ba-workflow-orchestrator`

Responsibilities:

- determine workflow;
- read state;
- decide next step;
- assemble context;
- invoke skills;
- invoke subagents;
- validate outputs;
- enforce human gates;

It should not perform every task itself.

# 33. Skill vs Subagent Rule

Use a **Skill** when:

- the task represents a repeatable method;
- one agent can perform it;
- the task does not need isolated long-running context.

Examples:

```text
extract-business-rules
generate-clarification-questions
build-data-model
generate-sequence-diagram
write-acceptance-criteria
analyze-impact
```

Use a **Subagent** when:

- context is large;
- work is independent;
- multiple tasks can run concurrently;
- the work would unnecessarily fill the main agent's context;
- specialization provides value.

---

# 34. Parallel Execution

Subagents may work in parallel when tasks are independent.

Example:

```text
EPIC-02

UC-007 ──→ Spec Subagent 1
UC-008 ──→ Spec Subagent 2
UC-009 ──→ Spec Subagent 3
```

All agents may execute concurrently if there are no dependencies.

Do not parallelize:

```text
UI Design
→ Sequence Analysis
```

if the sequence requires the approved UI.

Do not parallelize:

```text
Technical Review
→ Coding
```

because coding depends on technical approval.

---

# 35. Context Management

Do not send the entire product context to every subagent.

Before invoking a subagent, create a context package.

Example:

```yaml
task: "Specify UC-007"

context:

  product:
    - relevant product overview

  process:
    - BP-02

  use_case:
    - UC-007

  rules:
    - BR-003
    - BR-007

  entities:
    - Asset
    - Assignment

  screens:
    - SCR-014

  apis:
    - API-034
```

This reduces unnecessary context consumption and helps avoid context-window degradation.

# 37. Human-in-the-Loop Gates

The following gates are mandatory.

```text
GATE-01 CURRENT_STATE_REVIEW

GATE-02 OVERVIEW_APPROVAL

GATE-03 UI_MARKDOWN_REVIEW

GATE-04 HTML_PROTOTYPE_REVIEW

GATE-05 BA_SPEC_APPROVAL

GATE-06 TECHNICAL_APPROVAL

GATE-07 CRITICAL_FLOW_TEST

GATE-08 USER_GUIDE_REVIEW
```

When a workflow reaches a human gate:

1. save all artifacts;
2. update workflow state;
3. summarize what requires review;
4. stop execution;
5. wait for approval or comments.

Never infer human approval.

---

# 38. Review Feedback Loop

When reviewer comments are received:

```text
Review Comment
      ↓
Classify affected artifact
      ↓
Identify downstream artifacts
      ↓
Update source artifact
      ↓
Regenerate impacted downstream artifacts only
      ↓
Re-run validation
      ↓
Request approval
```

Example:

If BA changes a Business Rule:

```text
Business Rule
↓
Affected Use Case
↓
Validation
↓
Sequence/API if affected
↓
Acceptance Criteria
↓
Test Cases
```

Do not regenerate unrelated artifacts.

# 41. AI Behavioral Rules

All agents must follow these rules.

## Rule 1 — Never invent business decisions

If information cannot be derived from available evidence:

```text
mark it as OPEN_QUESTION or ASSUMPTION.
```

Do not silently invent the answer.

---

## Rule 2 — Distinguish current state from proposed state

Use:

```text
AS-IS
TO-BE
```

Never mix them.

---

## Rule 3 — Maintain stable IDs

Never randomly rename:

```text
UC-007
BR-012
API-034
ENT-005
```

IDs create traceability.

---

## Rule 4 — Reuse before creating

Before creating:

- API;
- Entity;
- Screen;
- Business Rule;

search current artifacts first.

Prefer reuse when appropriate.

---

## Rule 5 — Minimize unnecessary context

Agents must retrieve only the information necessary for the current task.

---

## Rule 6 — Never bypass approval gates

No coding before required specification/technical approval.

No workflow completion before required testing.

---

## Rule 7 — Treat AI output as draft until validated

Generated content must carry an appropriate status such as:

```text
DRAFT
WAITING_FOR_REVIEW
APPROVED
```

---

## Rule 8 — Improve the workflow from defects

If AI repeatedly produces an incorrect result, do not solve the problem only by manually correcting the final artifact.

Determine whether the root cause is:

```text
missing context
missing skill instruction
missing rule
incorrect workflow sequence
weak artifact schema
```

Then improve the reusable configuration so future executions improve.

---

# 42. Definition of Done

The BA workflow implementation is considered successful when the AI can execute the following scenario.

Given:

```text
an existing software product
+
a new business requirement
```

the system can:

1. understand the current product from repositories;
2. reconstruct current architecture and behavior;
3. process stakeholder requirements;
4. identify missing requirements;
5. produce overview analysis;
6. construct business processes;
7. produce business rules;
8. produce data models;
9. produce use cases;
10. create/update BA Knowledge Graph;
11. create a delivery backlog;
12. select an Epic or Use Case;
13. generate functional UI;
14. stop for BA review;
15. generate interactive prototype;
16. stop for BA review;
17. generate sequence analysis;
18. derive API specifications;
19. derive validation rules;
20. generate Acceptance Criteria;
21. compile a code-ready BA specification;
22. request technical approval;
23. implement approved functionality;
24. generate and execute tests;
25. compare actual behavior with requirements;
26. repair eligible defects;
27. request human testing for critical flows;
28. generate user documentation;
29. update all tracking artifacts;
30. later process a CR by analyzing impact through the BA Knowledge Graph.

The AI must be capable of stopping and resuming the workflow at any point without losing progress.

# 44. Implementation Priority

Do not attempt to build the full workflow at once.

Implement in this order:

```text
1. Workflow state management
2. Artifact structure
3. BA Planning / backlog
4. BA Specification Engine
5. Human approval mechanism
6. BA Knowledge Graph
7. Reverse Engineering Engine
8. Elicitation + Overview Engine
9. Technical Review workflow
10. Coding Engine integration
11. QA Engine
12. User Guide Engine
13. CR / Impact Analysis Engine
14. Hooks / external integrations
```

The first usable milestone should be:

```text
Use Case
→ BA Spec Engine
→ Human Review
→ Code-ready Specification
```

Then expand outward toward elicitation on the upstream side and coding/QA on the downstream side.

This avoids attempting to automate the entire SDLC before the core BA artifact pipeline is stable.
