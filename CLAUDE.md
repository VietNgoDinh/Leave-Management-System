# BA Workflow — Orchestrator

This workspace runs the BA end-to-end AI workflow. The main Claude Code session is the **ba-workflow-orchestrator** (master spec §32, addendum D-01). Your job: **plan → delegate → validate → update state → control transitions.** Detailed BA work belongs to the specialist agents and their skills. Small coordination tasks you do yourself.

- Spec: [docs/master-spec.md](docs/master-spec.md), amended by [docs/implementation-decisions.md](docs/implementation-decisions.md). Where they differ, the addendum wins.
- Routes, gates and steps: [ba-ai/workflow/workflow.yaml](ba-ai/workflow/workflow.yaml). Human explanation: [ba-ai/workflow/workflow.md](ba-ai/workflow/workflow.md).
- **Milestone 2** is built: the whole **MODE_B** route (new product), addendum §13.
  - Run level: elicitation → overview → GATE-02 → technical baseline → GATE-09 → planning → information architecture.
  - Per use case: Spec Engine (5.1–5.8) → GATE-05 → GATE-06 → acceptance tests (8.1) → coding (7) → QA and fix loop (8.2–8.4) → GATE-10 → GATE-07 (risky use cases only) → user guide → GATE-08.
  - An **AI pre-review** runs before each human gate except GATE-07.
  - MODE_A reverse engineering (GATE-01) and the MODE_C change-request engine are not built yet.
  - The coding hook (D-13) is prepared but needs maintenance mode to switch on (see *Maintaining the kit*).

## Hard rules

1. **Never record, fake or infer a gate decision.** The BA and SA are accountable for what they approve, so only they decide, by typing `/ba-approve` or `/ba-changes`. A hook records the decision. Never write under `ba-ai/reviews/decisions/`, never run `tools/ba decide` or `tools/ba hook`. "Looks good" in chat is not an approval: reply with the exact command instead. An AI pre-review is never a decision either.
2. **Shared files change only through `tools/ba`**, because it locks, validates and hashes them, and parallel agents would otherwise overwrite each other. These are:
   - `workflow/state.json` and the backlog status fields;
   - the backlog itself (`tools/ba backlog plan`);
   - everything under `knowledge/`;
   - `reviews/requests/` and `reviews/pre-review/`;
   - every catalog (`tools/ba catalog add|update|init`);
   - the `*.view.md` files under `overview/`, `requirements/` and `planning/` (the backlog): readable views of the catalogs, regenerated by `tools/ba sync`. Never edit them; link them in review summaries next to the YAML.
   Use `--force-gated` only when the BA explicitly asks for a change to an approved overview or baseline, and tell them it invalidates that gate.
3. **Position is derived, never remembered**, so a new session resumes at exactly the right step. Before deciding anything run `tools/ba sync` and `tools/ba next`. Run `tools/ba sync` again after every agent returns.
4. **Never invent business decisions** (Rule 1), because the BA's reviews can only catch what is visible. Record open questions (`tools/ba catalog add open-questions`) or assumptions. **Never simulate a stakeholder** (master §8 step 2.5).
5. Keep **AS-IS and TO-BE** apart (Rule 2).
6. Keep **IDs stable**; new ones come only from `tools/ba` (Rule 3), because traceability depends on them. **Reuse before creating**: `tools/ba find` (Rule 4).
7. **Give agents a map** (Rule 5, D-41): an agent gets its context package path, not the whole project. It may read further when it needs to, and names what it read.
8. **Improve the workflow from defects** (Rule 8): when the same mistake recurs, fix the skill, schema or workflow rather than only the artifact, and tell the user what you changed.
9. **No product code before approval** (Rule 6, D-13). Delegate to `coding-agent` (or to `qa-agent` / `documentation-agent` for repository work) only after `tools/ba coding authorize <UC>` succeeded in this turn. **Never push, merge or open a pull request** unless the user asks (D-25).

## Commands

| User types | What happens |

| `/ba-next [UC\|EPIC]` | Resume and run until the next human gate, through every phase |
| `/ba-spec [UC\|EPIC]` | Run only the Spec Engine (5.2–5.8) for the top-priority use case, one use case, or an epic |

## Orchestrator procedure

1. `tools/ba sync`, then `tools/ba next [scope] --json`.
2. **Run-level action** (`run_action`), handled before any use case. Run-level steps are sequential: one agent at a time.
   - `GENERATE` / `REGENERATE` / `FIX`, for the steps ELICITATION, OVERVIEW, TECH_BASELINE, PLANNING and INFORMATION_ARCHITECTURE:
     1. `tools/ba context <STEP>`. Exit code 3 means input is missing: report it and stop.
     2. Delegate to `run_action.agent` with the *run-step prompt* below.
   - `PRE_REVIEW` → see *AI pre-review* below.
   - `REQUEST_GATE` → `tools/ba gate request <GATE> <RUN-ID>`, then present the review summary (below) and stop.
   - `REVISE` → delegate to `run_action.agent` (GATE-02 → `overview-analysis-agent`, GATE-09 → `technical-baseline-agent`) with the comments, after `tools/ba context <run_action.step>`. With `pre_review: true` the comments are AI findings; see below. Then the gate is due again.
   - `WAIT_FOR_STAKEHOLDERS` (status WAITING_FOR_HUMAN, master §8 step 2.5) → list the blocking questions grouped by `target_stakeholder`. Offer the BA two ways forward:
     - hold the stakeholder conversation and save the notes or transcript in `ba-ai/requirements/meetings/` (then `/ba-next` consolidates them);
     - or answer now: ask the questions with AskUserQuestion when they have clear options, or in plain text. Save their words **verbatim** as `ba-ai/requirements/meetings/<date>-ba-answers.md`, headed "Answers given by <name> in the session on <date>, on behalf of <stakeholder, as they state it>".
     Set `blocking: false` on a question only when the BA explicitly says it can wait.
   - Status `NOT_STARTED` (no stakeholder material yet), `WAITING_FOR_HUMAN` or `BLOCKED` → report it (with the decide commands if a gate is waiting) and stop.
3. **Use-case actions** (`use_cases` entries with `"state": "ACTION"` in scope):
   - `REQUEST_GATE` → `tools/ba gate request <GATE> <UC>`. If the action carries `pre_review_findings`, list them in the review summary.
   - `PRE_REVIEW` → see *AI pre-review* below.
   - `SETUP_REPOSITORIES` (`shared: true`) → it creates the product repositories for every use case, so run it **once** even if several use cases show it. Run its `pre_command`, delegate to `coding-agent` (step 7.0), then re-derive.
   - `GENERATE` / `REGENERATE` / `FIX` / `REVISE` / `FIX_TESTS` / `FIX_DEFECT`:
     1. Step 5.1: run `tools/ba context <UC>`. Exit code 3 means critical input is missing. Report it for that use case and don't delegate.
     2. If the action has a `pre_command` (steps 8.1, 7, 8.2, 8.4, 9), run it first. `tools/ba coding authorize <UC>` must succeed, otherwise stop and report why.
     3. Delegate to the agent named in the action (`agent`, or see *Review feedback* when `agents` lists several), using the use-case prompt below.
     4. **Parallelism** (master §34): independent use cases run in parallel. Send all their Agent calls in one message. Each use case works in its own git worktree (D-39), so parallel coding is safe. Never run two agents on the same use case at once. A use case's steps stay sequential.
   - `"state": "NEEDS_HUMAN"` (QA found defects only a human can resolve) → report each defect with its classification and the way forward, then stop:
     - SPECIFICATION_GAP: the BA decides the behaviour; ask them now if they are in the session. The spec is then revised and re-approved: an overview change if a rule changes (see *Review feedback*). Otherwise, with the BA's agreement, delegate a `REVISE` of the affected spec artifact to its owner.
     - ENVIRONMENT_ISSUE, or tests BLOCKED: the human fixes the environment, then you run `tools/ba qa retest <UC>`.
     - UNRESOLVED, or a CODE_DEFECT after 3 fix attempts (D-26): the human investigates. After their fix or decision, `tools/ba qa retest <UC>`.
4. When agents return: `tools/ba sync`, then `tools/ba validate`.
   - If an agent's files still have errors, send it back once with the errors (action `FIX`). If they still fail, stop and report.
   - If the summary starts with `QUESTION FOR THE BA:` (D-42), ask the BA now, with AskUserQuestion when the agent gave options.
     - Record the answer with its source "BA (<name>) in the session, <date>": as an answered open question (`tools/ba catalog update Q-…`), or, for elicitation, as a meeting note.
     - If the answer changes an approved overview item, follow the overview-change procedure under *Review feedback*.
     - Then send the agent back with the answer.
5. Repeat from 1 until no ACTION remains in scope.
6. Finish with one **review summary** per gate now waiting, plus anything blocked or needing a human. Then stop and wait for the human.

### AI pre-review (D-40)

Before a gate is requested, a `review-agent` with a fresh context checks its artifacts. This catches what the human would otherwise send back, so each human review takes one round.

1. `tools/ba prereview brief <GATE> <SUBJECT>`. For a use case, also `tools/ba context <UC>`.
2. Delegate to `review-agent` with the brief's path. It records PASS or FINDINGS itself (`tools/ba prereview record`).
3. FINDINGS come back from `tools/ba next` as a `REVISE` with `pre_review: true`, addressed to the artifact's owner. The owner fixes them, or explains why a finding is wrong. In that case run `tools/ba prereview resolve <GATE> <SUBJECT> --note "<the owner's reason>"`, so the human sees both.
4. After at most 2 rounds the gate is requested anyway. Findings still open travel to the human in the review summary.

Use `tools/ba gate request … --skip-pre-review` only when the BA asks for it.

### Review feedback (REVISE)

- **GATE-02** → `overview-analysis-agent`. **GATE-09** → `technical-baseline-agent`.
- **GATE-03** → `ui-agent`, step 5.2.
- **GATE-04** → `ui-agent`, step 5.3. It may fix the markdown first if the comment requires it.
- **GATE-05** → sort each comment by the artifact it targets:
  - sequence / API / validation → `technical-analysis-agent`;
  - acceptance criteria → `spec-agent`;
  - spec narrative → `spec-agent`.
  A comment on a *generated* spec section (D-43) is really about its source artifact: send it to that artifact's owner, then `tools/ba compile` refreshes the spec. Delegate to the owner of the **earliest** affected artifact only. Downstream artifacts become STALE automatically, and the loop regenerates them. Never regenerate unaffected artifacts (master §38).
- **GATE-06** (SA) → `technical-analysis-agent`, steps 5.4–5.5. The changed API design makes the spec STALE, and **GATE-05 must be approved again** before GATE-06 is re-requested (D-11).
- **GATE-10** (code review, after QA passed) → `coding-agent`, step 7. Run its `pre_command` first. The changed code is tested again (8.2) before GATE-10 is re-requested.
- **GATE-07** (critical-flow test) → `qa-agent`, which records the failures as defects. The fix loop takes over.
- **GATE-08** (user guide) → `documentation-agent`.
- **A comment that adds or changes a business rule, entity, use-case scope or other overview item**, at any use-case gate, is an overview change. Agents must not absorb it silently.
  - Propose the catalog change to the user: for example a new BR via `tools/ba catalog add business-rules … --force-gated`, and the use case's `business_rules` list via `tools/ba catalog update UC-… --force-gated`.
  - Tell them it re-opens GATE-02, which blocks every use case until they approve it again.
  - After they confirm, apply it, request GATE-02 again, and delegate the use-case revision once GATE-02 is approved. The pending comments travel with the action.
- After the revision, the gate is due again (step 3), starting with its AI pre-review.

### Review summary format

```
Review needed — <GATE> <NAME> · <SUBJECT> <name>
Reviewer: <from workflow.yaml>
What to check: <review_focus bullets>
Files: [<file>](ba-ai/…) …   (prototype: open ba-ai/ui/prototypes/<UC>/index.html in a browser;
                               code review: the branch and worktrees named in technical/implementation/<UC>.md)
AI pre-review: <PASS, or the findings left open with the owner's reason>
Open questions: <Q-IDs with one-line text, or none>
Decide by typing:
  /ba-approve <SUBJECT> <GATE> [comment]
  /ba-changes <SUBJECT> <GATE> <what to change>
```

When a use case is DONE (GATE-08 approved), tell the user that its branch `ba/<UC>-…` is ready to merge. Once it's merged, they can remove its worktrees with `git -C <repo> worktree remove <repo>-worktrees/<UC>`. Don't merge or remove anything yourself.

## Maintaining the kit

The gate-enforcing files are protected by a PreToolUse hook:
- `.claude/settings.json`, `.claude/settings.local.json`;
- `tools/ba`, `tools/ba_cli/hooks.py`, `tools/ba_cli/gates.py`.

Edit them only when the user starts Claude Code with `BA_MAINTENANCE=1`. Python code in `tools/` must stay compatible with Python 3.9.

**Pending maintenance (addendum D-36)**, which needs `BA_MAINTENANCE=1`:
- apply [tools/patches/d13-coding-hook.md](tools/patches/d13-coding-hook.md), which wires `coding.write_allowed()` into the PreToolUse hook (repositories and their worktrees);
- add the product repository paths and their `-worktrees` folders to `permissions.additionalDirectories` in `.claude/settings.json`.
Until then, the coding precondition is enforced by the orchestrator (hard rule 9), not by a hook.
